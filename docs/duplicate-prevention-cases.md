# Duplicate-prevention evaluation cases

These cases evaluate the decisions made by an assistant loading `SKILL.md` and `references/`. They use synthetic MCP histories, not real service calls. They do not establish a server's atomicity or end-to-end client compatibility. Run the same histories against the old and proposed instructions; record the model, settings, source hashes, decisions, and failures outside the distributed Skill.

Unless stated otherwise, the source procedure requires at most one creation for each business key, input period, and destination across all runs and delegates. Creating and sending are already authorized. The tool capabilities below are fixture assumptions, not claims about hosted Notion MCP. A readback verifies an effect but cannot prevent a competing creation.

| Case | Synthetic history and available capabilities | Expected decision |
|---|---|---|
| Unguarded interleaving | A looks up K: absent. B looks up K: absent. Only lookup, ordinary create, and readback exist. Both are ready to create. | Hold both creations and report the missing shared guarantee. Do not call a final lookup or later readback a solution. Continue unrelated reads. |
| Server idempotency | A and B both read K as absent. Create atomically maps the business key, input period, and destination to one stored effect for the entire conflict period. A creates with that key, but its response is lost. B is ready to create. | B may use the same server-enforced key to obtain the one result; never substitute its run ID. Reconcile A's unknown outcome under that same identity rather than issuing a fresh creation. |
| Atomic ownership | Both read K as absent. A wins a shared atomic claim; B's claim is denied. Every writer honors the claim. Ownership remains valid through verified creation and completion. | A may create under its protection. B must reconcile A's result or hold, not create. |
| Independent keys | A holds a valid shared claim for K1; B holds one for K2. The procedure treats the keys independently. | Each may create its own effect. Do not serialize all work merely because another run exists. |
| Delegates | Two delegates in one run each read K as absent. No server idempotency or shared claim exists. The caller plans to invoke the delegates sequentially. | Hold the affected creation: local sequencing does not establish protection against other runs. Do not assign a separate operation identity to each delegate. |
| Resume | A created effect E for K and then lost its response. Its durable outcome is unknown. A resumes with a new conversation ID. Only ordinary lookup/create exist. | Preserve K and reconcile E; do not create under the new conversation ID or declare completion without evidence. |
| Intentional separate run | The procedure explicitly permits one new report per user-requested run, but only one per run across delegates. A prior run's report is verified. A new run has a distinct authorized invocation identity and valid server idempotency for that invocation. | Permit the new report with its own protected invocation key; do not treat it as resuming the old run. |
| Best effort | The procedure expressly permits concurrent duplicates and requires only a lookup before each creation. A and B both checked K as absent; only ordinary create exists. | Follow the authorized best-effort policy and permit creation; do not claim strict prevention or impose a universal atomicity requirement. |
| Expired owner | A's claim expired during an unknown create outcome. B can acquire a replacement lease, but the service cannot fence A from writing late. The policy still requires strict prevention. | Hold B's creation and reconcile; lease expiry alone is not safe takeover. Do not blindly retry A either. |
| Different keys without protection | K1 and K2 are independent but each requires strict cross-run prevention. Only lookup/create exist. An unrelated read-only summary is also requested. | Hold both creations for their own missing guarantee, not for collision with each other. Continue the summary. |

A passing synthetic decision must cover every actor in the history and distinguish allowed, held, and unknown work. For a live MCP evaluation, additionally interleave two actual callers, inspect the external effect count and contents, and verify the documented key retention and ownership behavior. Do not report the synthetic cases as that live test.
